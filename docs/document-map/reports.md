# `reports/`：检查过什么，发现了什么

`docs/reports/` 保存审查与交付材料。需求、设计和合同描述**打算做成什么**；报告记录**某次检查实际看到了什么**。因此，任何“通过”都要连同检查对象、版本、范围和证据一起理解。

| 子目录 | 文件类型 | 主要回答的问题 |
| --- | --- | --- |
| `review/` | `REV-*`、`RESULT-*` | 规格或交付是否与上游承诺一致？发现了哪些缺口？ |
| `qa/` | `QA-*` | 工程质量、测试和场景覆盖检查得怎样？ |
| `e2e/` | `E2E-*` | 在真实浏览器里，用户路径是否按预期走通？ |
| `bugs/` | `BUG-*` | 问题如何出现、原因是什么、修复边界与复验结果是什么？ |
| `acceptance/` | `ACC-*` | 一项 REQ 的要求有没有逐项得到当前证据支持？ |
| `release-audits/` | 发布审计 | 跨模块、数据、部署和恢复等系统风险是否已核对？ |
| `design-foundation/` | Foundation 回放 | 多次界面工作之后，整体体验设计是否仍成立？仅在条件出现时使用 |

这些目录按**检查对象**分开：例如 QA 的结论不能代替浏览器里走过的用户路径，某个缺陷修好也不能代替整项 REQ 的验收。`BUG-*` 提供人类可读的缺陷视图；调查和修复中的当前结构化事实仍须结合运行记录核对。

模板仓库里的 `*-template.md` 只是报告格式。目标项目里已有的一份报告也只适用于它记录的那轮检查；代码或需求改变后，旧结论需要重新核对。想知道报告对应哪个阶段，可查[机制原理](/mechanism/)；想知道原先要求什么，可回到 [`requirements/`](./requirements)。
