# `architecture/`：系统内部如何分工

`docs/architecture/` 保存技术设计。需求说明产品承诺，体验设计说明使用过程；这里进一步说明系统由哪些部分组成、数据怎样流动、状态如何变化。它把业务上的要求交给后续 [`dev/contracts/`](./dev) 使用。

| 位置 | 记录什么 | 常见查阅问题 |
| --- | --- | --- |
| `ARCHITECTURE-*.md` | 整体目标、系统边界、各部分职责、数据流、安全、性能、部署与回滚 | 一项能力应由系统哪部分承担？ |
| `data-model/` | 共享数据概念与原生模型的入口 | “订单状态”等数据在各部分是否同义？ |
| `state/` | 某个业务对象有哪些状态、允许怎样转换、谁有权限触发 | 已发货的订单还能取消吗？非法转换怎样处理？ |
| `dataflow/` | 数据从哪里来、到哪里去、是否敏感、如何保留和处理异常 | 取消申请经过哪些环节？相关数据如何保护？ |

先从主架构看系统分工，再按问题查数据、状态或数据流。页面与操作体验在 [`design/`](./design)，两边互相引用。

例如，订单状态的名称与取值要有共同定义。合同引用项目原有格式的模型文件，代码通过生成或校验实际采用它；后续检查再核对两端行为。相关约定见 [`dev/`](./dev)。

这里的文件名与子目录来自模板。某个目标项目实际产生哪些模型，要看需求与设计范围；目录里只有模板，并不表示已经完成技术设计。
