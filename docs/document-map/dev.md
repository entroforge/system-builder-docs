# `dev/`：约定怎样做，再安排谁来做

`docs/dev/` 分成 `contracts/` 和 `tasks/`。前者把需求与设计翻译成各部分都能遵守的约定，后者把约定拆成可以交接、检查的工作。合同回答“做成什么样”，任务回答“这一份工作交付什么”。

## `contracts/`：各部分对同一行为的约定

| 文件 | 主要作用 |
| --- | --- |
| `CONTRACTS-{id}.md` | 一项 REQ 的合同总索引：有哪些前端、后端、联调合同，需求点如何覆盖到这些合同 |
| `FE-{id}.md` | 前端应呈现的页面与状态、需要读取的原型、调用方行为和验收 |
| `BE-{id}.md` | 后端负责的规则、数据、权限、持久化及验收 |
| `SYNC-{id}.md` | 前后端之间共同遵守的接口、数据含义、错误、状态与恢复行为 |

以取消订单为例，前端需要知道何时显示操作与反馈，后端需要知道何时允许更改订单，双方还需要约定请求、响应和拒绝原因。三份分工合同通过 `SYNC` 对齐；`CONTRACTS` 帮助查清需求是否遗漏在分工之间。

## `tasks/`：一项工作怎样交付

| 文件 | 主要作用 |
| --- | --- |
| `TASK-{id}.md` | 单项工作的目标、可读输入、交付条款、允许范围、依赖、产物和完成判据 |
| `index-REQ-{id}.md` | 这一项 REQ 的整体任务索引与先后安排，包括哪些工作可以并行 |

任务文件提供工作边界，索引提供整体安排。实际正在执行什么、哪些成果已经进入共同版本，仍要查项目当前运行状态；任务正文中的计划不等于实时进度。检查工作质量和结果，则进入 [`reports/`](./reports)。
