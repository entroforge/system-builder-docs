# 打开项目的 `docs/`

一项软件工作会留下许多材料：需求、设计、任务、检查结果，还有支撑这些工作的规则。`docs/` 按**材料回答的问题**分目录。沿目录查阅，可以先看到项目拥有哪些资产，再进入某份文件的细节。

这里依据的是 `go-system-builder/docs/` 的实际编排。**模板仓库**主要放空白模板、规则、指南与合成示例；安装到**目标项目**后，才会逐步产生这项项目自己的 REQ、设计、合同、任务和报告。一个目录存在，不表示其中已有正式成果。

## 从目录看出编排逻辑

| 在项目中想弄清 | 进入哪一层 |
| --- | --- |
| **承诺了什么** | [`requirements/`](./requirements)：目标、范围、具体要求与验收 |
| **产品怎样呈现** | [`design/`](./design)：整体设计语言，以及各模块的故事、动线和 HTML 原型 |
| **系统怎样承担** | [`architecture/`](./architecture)：模块职责、数据、状态与流动 |
| **怎样交接工作** | [`dev/`](./dev)：前后端及联调合同、单项任务和整体计划 |
| **实际检查到了什么** | [`reports/`](./reports)：审查、质量、浏览器路径、缺陷、验收与发布审计 |
| **工作允许怎样推进** | [`control/`](./control)：阶段协议、合法迁移与受保护操作 |
| **遇到具体工作遵守什么约束** | [`rules/`](./rules)：变更、Git、安全、原型、缺陷等稳定规则 |
| **操作和背景怎么查** | [`guides/`](./guides)：安装、入门、概念与工程说明 |
| **完整样子是什么** | [`examples/`](./examples)：合成的共享模型、任务与报告样例 |

前五个目录承载项目逐步形成的内容；后四个目录提供共同规则和学习材料。阅读可以按左侧目录逐层展开。需要追查某份材料在 S0～S11 的哪一步产生，再进入[机制原理](/mechanism/)。

## 根目录的四个入口

| 文件 | 用途 |
| --- | --- |
| `docs/README.md` | 从整个工程文档进入各目录 |
| `docs/DOCUMENT-MAP.md` | 简短说明每类文档的职责与权威范围 |
| `docs/project.yaml` | 项目配置：目标、参与者、技术栈和约定路径等 |
| `docs/project-map-template.md` | 面向人的项目概况模板；目标项目填写后成为 `docs/project-map.md` |

`project-map.md` 方便阅读项目概况与下一步，却不保存唯一的当前运行事实。当前绑定的 REQ、阶段及证据状态要查 `docs/` **外**的 `.claude/loop-state.json`。实际代码和测试也在项目的代码目录，不因为文档引用了它们就搬进 `docs/`。

## 同一目录里，材料的身份可能不同

`REQ-template.md` 是空白样板，`REQ-{id}.md` 才是目标项目填写的需求；`examples/` 里即使出现 `REQ-042.md`，也仍是合成例子。`reports/` 中的一份检查记录只说明**它所指的版本和范围**发生过什么。先辨认模板、项目实例、示例与报告，再判断手里的材料能回答哪一个问题。
