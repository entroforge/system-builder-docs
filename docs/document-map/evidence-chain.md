# 从一条承诺查到交付证据

目录说明材料在哪，材料之间的引用说明一项要求怎样落实。判断交付时，可以选一条验收标准，沿它查看设计、分工与当前结果。

以下沿用“取消订单”的虚构例子，编号和结果用于说明阅读方法，均不代表真实项目成果。

## 先把要检查的结果说完整

假设 REQ 的 `AC-01` 约定：**顾客可以取消本人未付款、未发货的订单；看到取消成功后，重新打开订单，状态仍为已取消。**

这里同时要求操作成功、反馈正确、结果保存。后续材料要把这些要求交给合适的执行者，并取得相应证据。

## 同一条要求，怎样穿过目录

| 材料 | 这条承诺在其中变成什么 |
| --- | --- |
| `requirements/REQ-{id}.md` | `AC-01` 给出可判断的结果，并指回功能要求与原先目标 |
| `design/prototypes/orders/` | 故事说明顾客的处境；动线和 HTML 原型呈现取消与重新打开；场景包形成相关 CASE |
| `architecture/` | 确定谁检查订单归属、付款与发货状态，谁保存取消结果 |
| `dev/contracts/` | FE 约定按钮与反馈；BE 约定规则与持久化；SYNC 约定两端共同的数据和操作含义；总索引连接需求与条款 |
| `dev/tasks/` | 将条款交给具体任务，明确实现范围和完成判据 |
| `reports/` 与运行证据 | 记录共同版本中实际检查到的结果，包括规则检查、浏览器操作和状态核对 |
| `reports/acceptance/` | 汇总 `AC-01` 是否获得当前有效证据支持，说明剩余问题 |

每一层把上一层的要求展开成自己的职责。比如持久化由后端实现，页面反馈由前端呈现；两部分都要回到同一条顾客承诺。

合同和任务各有索引，适合沿引用查阅。后续任务声明自己承担哪些条款，检查记录引用被检对象；已经锁定的合同按变更规则维护。

## 一次核验，重点看四件事

1. **结论对应哪条承诺。** 验收材料应能指到 `AC-01`，再指到相应的检查情形与结果。
2. **检查了哪个版本。** 确认报告适用于当前共同版本和需求基线。版本编号、文件指纹等具体核对由机制承担。
3. **实际观察到了什么。** 成功提示、重新打开后的状态、业务规则与数据变化，分别要有适合它们的证据。截图能展示可见状态，持续保存还需相应检查。
4. **还缺什么。** 必需的检查情形未执行、被阻塞或没有结果，应保留为缺口；真正不适用的项目需说明理由并接受审查。

其他验收标准还应覆盖已发货、非本人订单等拒绝情形。检查围绕同一套场景展开，才能看见允许、拒绝和恢复是否齐全。

## 通过与不足，各是什么样

**证据支持这条承诺：** 当前共同版本中，规则检查确认该订单允许取消；浏览器操作取得成功反馈，重新打开后仍显示已取消；相应结果都有版本和对象引用，也没有相关未解决发现。

**证据仍不足：** 报告只给出成功提示截图；或者报告检查的是修复前版本，尚未检查修改后的状态保存。此时可明确要求补上“当前版本重新打开后的结果”，再由团队选择检查办法。

一次核验只能说明所查承诺。整项 REQ 的验收还要逐项检查其余要求与系统风险。例子中的方法，可以用于挑查关键承诺；完整覆盖由 AI 团队和机制共同维护。

发现偏差后，沿这条链找最早失真的材料，再查[对应阶段](../mechanism/)。团队怎样报告进度与待决定事项，见[把握进度与干预](../engineering/management)。
