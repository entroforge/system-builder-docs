# `requirements/`：一份 REQ 说清什么

`docs/requirements/` 保存一项项需求。模板仓库提供 `REQ-template.md`；目标项目填写后，才会出现 `REQ-{id}.md`。一份 REQ 要让不同人对**为什么做、选什么方向、最终承诺什么**形成同一理解，因此模板从 §A 排到 §C。后面的 §D～§F 保存澄清、确认和追溯记录。

## §A：先确认想改变什么

| 模板中的位置 | 记录什么 | 为什么要有 |
| --- | --- | --- |
| A1 预期效果 | 把最初的想法整理成两三句明确的目标，再由人确认 | 为整项工作留下共同起点 |
| A2 背景与痛点 | 问题出现的情境，以及现在没有这项能力时如何应对 | 避免只修表面症状 |
| A3 成功长什么样 | 完成后使用者能够感受到的变化 | 后面判断交付是否有意义 |
| A4 明确不做 | 本次不承担什么，以及理由 | 给范围画边界，避免相邻问题悄悄混进来 |
| 用户和利益相关者 | 各方诉求与决策权 | 发现诉求冲突时，知道哪些需要人的取舍 |
| 术语 | 关键业务词的含义与容易混淆的叫法 | 后续设计、合同和任务用同一种语言 |

以“允许顾客自行取消订单”为例，A3 可以描述顾客完成取消后看见明确结果；A4 则可以说明本次是否承担退款到账时间。这个例子只展示字段分工，实际承诺由具体项目决定。

## §B：比较方向，留下取舍依据

| 模板中的位置 | 记录什么 | 为什么要有 |
| --- | --- | --- |
| 方向取舍 | 候选做法、选定方向、放弃其他方向的理由 | 之后有人质疑方案时，可以回到当时的判断 |
| 硬约束 | 必须遵守的条件及其不可打破的原因 | 区分真正的限制与个人偏好 |
| 关键假设与风险 | 尚未证实的前提、影响和验证办法 | 让不确定性保持可见 |

这里确定的是**需求方向的边界**。技术架构如何实现，另在 [`architecture/`](./architecture) 中展开。

## §C：把承诺写成能逐项核对的要求

| 模板中的位置 | 记录什么 | 查阅时关注什么 |
| --- | --- | --- |
| 需求点 `FR-*` | 功能要求、涉及的模块或流程、优先级，并指回 §A | 每一项是否服务原先的目标 |
| 流程和异常 | 输入、输出、状态、失败情形与权限 | 正常情况以外，拒绝、错误和无权操作会怎样 |
| 验收标准 `AC-*` | 可以判断是否兑现的标准，指向需求点、非功能要求或明确不做项 | 判断依据是否具体，是否有来源 |
| 非功能需求 `NFR-*` | 性能、安全、可靠性、合规等质量要求及证据 | 功能可用之外，质量底线是什么 |
| 数据迁移范围 | 迁移、保留、删除或检查的文件与依赖 | 改动已有系统时，哪些资产会受影响 |
| UI 影响 | 页面、组件、交互、可见状态是否变化及设计引用 | 是否需要更新 [`design/`](./design) 中的模块原型 |

§C 将“希望顾客能取消订单”拆成可核对的情形：符合条件时能成功取消，不符合条件时要说明原因，权限不足时不能改变订单。`FR` 是要求，`AC` 是怎样判定要求得到满足；两者相互指向。

## §D～§F：留住尚未解决与已经确认的事

- **§D 待澄清问题**记录问题、影响范围、是否阻塞和最终结论。不能确定的业务规则会留在这里，直到有依据再作决定。
- **§E 锁定与逐层拍板**记录 §A、§B、§C 的人类确认及最终锁定。明确的确认会落到文档里，便于之后追溯。
- **§F 派生文档与覆盖矩阵**保留锁定时的下游索引快照。后续持续更新的覆盖关系由 `docs/dev/contracts/CONTRACTS-{id}.md` 维护；阅读本次承诺时，先看 §A～§C。

这套排列让需求从意图逐步变成承诺。想查某个页面或交互的具体设计，沿 §C 的 UI 影响进入 [`design/`](./design)；想查承诺如何被分派，进入 [`dev/`](./dev)。
