# 怎样交付一次软件变化

一个购物网站希望增加自助取消。交付时，顾客能找到入口，系统按规则处理订单，页面显示真实结果，运营人员有上线和恢复办法。

这些部分需要**在同一个版本中共同成立**。因此，工作按五个选择展开：确定变化、约定配合、分工集成、取得证据、决定发布。

下面沿用“顾客取消本人未付款、未发货的订单”的教学假设。文中的 **S0～S11** 是模板的阶段编号，详细输入输出可在[机制原理](/mechanism/)查阅。

## 1. 每次推进一项边界清楚的变化

“完善订单系统”可能同时包含取消、退款、售后和通知。一起展开，某个部分迟迟未完成时，很难说清哪些成果已经可以交付。

先选一项能独立判断的变化：**符合条件的顾客能够自行取消订单，并知道结果。** 这项变化会涉及页面、订单服务和数据；退款时效等可独立讨论的目标，另行安排。边界按用户结果划分。

模板将这份承诺记为 **REQ（需求确认稿）**。S0 确认范围与验收；S1 登记需求、开发起点、成果汇入的开发分支和发布目标。本轮围绕一项 REQ 推进，内部可以有多个并行任务。

需求保存在项目的 `docs/requirements/`。代码与文档通过 Git 的**提交**留下确定版本，说明“在什么已有能力上做这次变化”。本次承诺与开发起点都要明确。

## 2. 先约定配合方式，再分工

若只分派“AI A 写页面、AI B 写接口”，A 可能在点击后立即显示成功，B 却只表示请求已收到。各自完成，顾客仍可能看到错误结果。

因此，先确定取消条件、状态变化、成功与拒绝的反馈，再约定前后端交换什么数据。**契约**就是各部分共同遵守的行为与接口约定。任务根据契约拆分，检查也以它为依据。

准备工作据此安排：S2 设计，S3 契约，S4 任务与依赖，S5 独立检查是否一致、能否执行。设计进入 `docs/design/` 和 `docs/architecture/`，契约与任务进入 `docs/dev/`。

AI 依据共同约定自主选择实现。人确认业务条件与代价；设计若要放宽取消条件，再交人确认。

## 3. 分开工作，汇入同一个版本

页面与接口可以并行开发，但同时编辑同一工作目录，容易覆盖彼此的修改。各任务从明确的已提交版本开始，在独立分支和 **worktree（关联的工作目录）**中工作，完成后提交成果。

成果随后合入指定开发分支，形成**共同版本**。联合检查通过并被接收，才完成任务交接。整体验证再检查所有部分能否一起工作。

所以 S6 同时包含实现与集成。提交和合并记录保留改动来源；任务与接收记录说明允许改什么、实际交回什么。分支提供工作路线，任务和运行机制管理写入范围。

具体过程见[从一行变更到共同版本](/start/git)。

## 4. 用当前版本的证据判断结果

页面和接口各自通过测试，仍可能在一起运行时出错。例如接口返回 `status`，页面却读取 `cancelled`。Git 可以顺利合并这样的代码，实际操作依然失败。

S7 因此独立检查共同版本：实现是否符合约定、工程质量是否达标、真实使用路径能否走通。报告要说明检查了哪份需求、哪个版本、哪些场景，以及得到什么结果。

发现问题后，S8 调查原因与影响，S9 按明确范围修复。修复改变了代码，受影响的旧结论也要重新取得证据；原问题复验通过后，再回到完整验证轮。

依据保存在 `docs/reports/` 与运行证据中。**“通过”需要说明检查对象和范围。** 承诺若改变，则暂停，由人确认修订，再重新建立设计和证据。

具体示例见[冲突、版本与发布](/start/git-decisions)，承诺与检查的对应关系见[从承诺查到证据](/document-map/evidence-chain)。

## 5. 开发接收与发布分别决定

开发分支会持续接收工作，运行中的用户需要一个经过确认的发布版本。本模板为此分开两个目标：**开发分支**承载日常集成，**发布上游**保存正式发布快照。目标由项目明确指定。

S10 对照需求汇总验收，同时检查系统风险、部署、数据迁移和恢复安排。S11 把这些材料交给人决定：是否交付，何时发布，是否接受已列出的风险。实际发布由人执行。

任务进入开发分支时保留合并历史；正式发布时，将已确认的开发改动汇成发布提交（称为 **squash，压缩提交**），发布后再合回开发分支。前者便于逐项追查，后者留下一次发布的整体快照。发布范围要与验收依据对应，下一批功能另行开发。

发布提交保存交付内容，推送把它传到远程仓库，部署让它在实际环境运行。交接还要说明上线与恢复办法，见[运维与发布](./operations)。

## 一份可以用于交接的说明

一次交接可以按上述顺序说明：

> **本次增加：** 顾客自助取消本人未付款、未发货的订单；退款时效保持现有规则。\
> **开发起点：** 已确认的需求稿，以及开发分支中的确定提交 B0。\
> **必须共同成立：** 允许与拒绝规则一致，订单状态正确，页面反馈与服务端结果相符。\
> **集成目标：** 页面与接口任务合入指定开发分支，在共同版本 M1 上完成检查。\
> **发布依据：** 对应 M1 的验证、验收与审计材料，已知风险、部署及恢复安排，人的明确决定。

B0、M1 是示例代号。实际项目记录可追查的提交标识；发布内容发生变化时，也要核对相应依据。

人先看这份交接，再按需核对关键承诺或异常，无需逐行审阅代码。AI 承担专业工作，留下可复查的结果。
