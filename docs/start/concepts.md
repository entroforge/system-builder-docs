# 工作中的几个词

遇到陌生词时，可以在这里按问题回查。每组概念都用取消订单说明它指什么、怎样影响协作。

## 一次操作经过哪些部分

取消订单时，**前端**呈现页面、接收操作并显示反馈；**后端**检查订单归属与业务条件，处理取消；**数据存储**保存结果，供下次读取。

各部分通过**接口**交换信息。接口约定怎样提出请求、怎样返回结果。**数据模型**进一步约定信息的结构与含义，例如订单状态有哪些取值。前后端分离，就是将页面与服务端的职责分开实现，通过共同约定协作。

按钮出现以后，还要检查业务操作是否完成、结果是否保存、失败如何反馈。

## 模块与业务语言

**模块**是系统中承担一组相关职责的部分。讨论产品时，可以先按订单、支付等能力理解；具体技术边界由设计确定。

**领域驱动设计，简称 DDD**，强调从业务知识出发建立模型，并在明确的业务范围内使用一致语言。例如“订单取消”与“退款完成”表达不同结果，产品、开发和测试需要把含义说清。

DDD 中的**限界上下文**，是某套业务模型与语言适用的范围。例如仓储说“完成”，可能指发货完成；交易说“完成”，可能还要求顾客收货。协作需要说明这个词属于哪个范围。上下文帮助划清词义与模型边界，代码模块和 REQ 则分别承载实现分工与一次变化。

这个视角帮助澄清职责与词义，具体架构由项目设计确定。

## 一次变化与验收

**REQ** 是一项需求的确认稿，写明本次要改变什么。**任务**是为兑现它而分派的一份工作。一项取消订单 REQ 可以包含页面、规则、测试等任务，并影响多个持续存在的模块。

**验收标准 AC** 表达怎样判断要求已满足，例如取消成功后重新打开订单，状态仍为已取消。**检查情形 CASE** 表达一次具体检查的条件、动作和预期结果。一个标准可能需要成功、拒绝、失败等多个情形共同检验。

**契约或合同**是不同部分共同遵守的技术约定。在这里，它说明输入输出、状态、错误与职责；FE、BE、SYNC 分别指前端、后端与双方协同的约定。

## 状态与允许的变化

订单可以处于待付款、待发货、已发货等状态。某个动作能否改变状态，还取决于条件和权限。

**有限状态机，也称有限状态自动机**，用有限的一组状态，以及事件、条件和转换，描述这些允许的变化。可以把它理解为一张“目前是什么、发生什么后可以去哪”的规则表。

订单状态描述业务对象；需求工作阶段描述开发过程；REQ 文件的草稿、锁定等状态描述文档。分别看清所指对象，才能避免混淆“需求已确认”和“软件已完成”。

## 依赖与并行 {#依赖与并行}

若页面与后端都要使用一份共同定义，就需要先确定这份定义。**依赖图**用箭头标出“谁必须先有哪项结果”。

任务前置依赖组成**有向无环图，简称 DAG**：箭头有方向，沿依赖不会绕回自身。若甲等乙、乙又等甲，两项工作都无法开始，就需要调整拆分。

依赖齐备后，互不依赖且没有资源冲突的任务可以并行。这里限制的是任务前置关系；验证失败后返回调查和重验，属于允许重复经过的工作流程。

## 版本与工作区 {#版本与工作区}

**Git** 保存代码和文档的版本历史。一次**提交**留下当时的版本记录；**分支**为一条开发路线命名，方便持续提交与追踪；**合并**把另一条路线的成果接到当前路线中。

**worktree** 是同一个 Git 仓库关联的另一份工作目录，可以检出不同分支，让多项工作在各自目录展开。分支管理版本路线，worktree 提供实际编辑空间。

本模板在 S1 同时确定两个目标：**开发分支**接收各任务的成果，形成供整体验证的共同版本；**发布上游**明确本轮最终交付的 Git 目标，涉及远程仓库时还要注明远程名称。两者分别说明“工作汇到哪里”和“获准后把版本交到哪里”，需要明确登记。

任务按约定从已提交的开发基线展开，再交回开发分支，接受检查。进入开发分支不会自动推送到发布目标；发布仍需人的批准与实际操作。具体分支名由项目确定。

完整示范见[从一行变更到共同版本](./git)与[冲突、版本与发布](./git-decisions)。

## 基线、指纹与证据

**基线**是本轮共同依据的确定版本。**指纹**是由文件内容计算的摘要，帮助程序识别内容是否改变；它无法判断内容是否正确。

**证据**是实际检查留下的结果与材料。它需要说明检查了什么、哪个版本、哪些情形，以及观察到什么。代码或承诺改变后，要重新核对旧证据的适用范围。

验证中的 **QA** 关注工程质量；**E2E** 是端到端检查，本模板中适用的用户界面路径需要在真实浏览器里取得证据。两者检查的对象不同。

## 团队与工程控制

**Agent** 是承担工作的 AI，主会话负责协调，专职角色承担设计、执行或独立检查。**Runtime** 是运行状态，记录当前事实；**Harness** 是执行校验与登记的程序；**Hook** 在相关工具操作前后触发检查与反馈。

**工程控制**就是先定目标，观察结果，发现偏差后查明来源、纠正并再检查。例如重复提交仍会导致两次取消，先重现并调查原因，再修复和复验。看新增证据与剩余问题，判断是否真正有进展。

这些词如何共同用于人的管理，见[工程协作](../engineering/)。如何把想法划成一项可交付变化，见[产品与需求](../engineering/product)。
