# 从一行变更到共同版本

[交付策略](/engineering/)要求各任务汇入共同版本后再接受检查。这里跟着一行代码，看这一策略怎样通过修改、提交、分支与合并落实。

以下使用简化的订单代码。文件、分支和版本标记都是教学示例。

## 一行改动，改变了一条行为

本次要求：顾客只能取消本人未付款、未发货的订单。现有代码已经检查付款与发货状态，需要补上订单归属。

```diff
 function canCancel(order, actorId) {
   return (
+    belongsTo(order, actorId) &&
     isUnpaid(order) &&
     isUnshipped(order)
   );
 }
```

`+` 标出新增的行；删除的行会以 `-` 标出。这种差异叫 **diff**。这里增加的是“操作者必须拥有订单”这一条件。

diff 让检查者找到改动。归属判断是否正确，还需要本人允许、他人拒绝的测试结果。

人可以据此反馈：

> 本次需要补的是订单归属检查。请说明这项改动和相关测试怎样覆盖本人允许、他人拒绝。

## 把相关改动留成一次提交

执行者完成归属判断、必要调用与测试，检查后组成一次相关提交，说明可以写为：

> 补齐取消订单的归属检查及允许、拒绝测试。

**提交 commit** 保存被 Git 跟踪文件的一次快照、父提交和说明，并获得确定标识。diff 比较两份内容；提交保存一个版本，可以包含多个文件和多行改动。

提交前有两个位置：**工作目录**放当前编辑的文件，**暂存区**收集准备纳入这次提交的内容。先看暂存区，可以发现无关改动是否混入；暂存之后继续编辑，也需要重新选择要提交的内容。

例如，这次权限修复和一次无关的首页配色调整可以分别提交。之后检查或撤回权限修复时，范围便能说清。

## 从共同起点分出两条工作路线

假设开发分支当前停在版本 **B0**。任务 A 补订单归属，任务 B 改善取消结果反馈。两项工作都从 B0 开始，分别形成 **A1** 与 **B1**。

![两项任务从共同提交 B0 分出，各自产生 A1 和 B1；先合入 A1 形成 M_A，再合入 B1 形成共同版本 M1，随后检查 M1。](/images/git-shared-version.svg)

B0、A1、B1、M_A、M1 是图中的教学代号，实际 Git 提交有自己的标识。箭头表示从已有提交形成后续提交，开发分支先接收 A，再接收 B。

**分支**为一条版本路线命名，指向这条路线当前的提交。新提交产生后，所在分支的指向随之向前。分支上的项目仍有完整文件，各任务按约定修改其中一部分。

## 工作目录与任务范围分别确定

这两项任务可以各有一个 **worktree**，即同一 Git 仓库关联的另一份工作目录：

| 工作 | 从哪里开始 | 在哪里编辑 | 获准改变什么 |
| --- | --- | --- | --- |
| A：订单归属 | B0 | 任务 A 的 worktree 与分支 | 归属判断、必要调用与相关测试 |
| B：结果反馈 | B0 | 任务 B 的 worktree 与分支 | 取消反馈与恢复路径及相关测试 |

worktree 分开编辑空间，任务约定与运行机制管理修改范围。一个分支上仍有完整项目，允许改哪些部分由任务和授权确定。

本模板从明确的已提交开发版本创建任务 worktree。主会话尚未提交的修改，不会自动出现在新工作目录中；必要输入要先交付或按约定交接。

## 将成果接回共同版本

任务 A 先交回 A1，开发分支接收它；随后再接任务 B 的 B1。合并时，Git 根据双方的共同祖先比较改动，尽可能组合这些变化。本模板的任务集成保留合并提交，以便追查交接来源。

最终共同版本 **M1** 应同时包含归属检查和结果反馈。此时还要在共同版本检查：本人订单能够完成取消，他人订单被拒绝，页面反馈符合真实结果。

局部测试检查各任务的版本，整体验证检查 M1 中它们一起运行的结果。

项目负责人可以要求一份这样的交接说明：

> A、B 的成果已经合入开发分支。请列出共同版本、联合检查结果和剩余问题。

若合并出现冲突，或无冲突却出现错误行为，继续阅读[冲突、版本与发布](./git-decisions)。
