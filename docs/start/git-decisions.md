# 冲突、版本与发布

本篇接着[交付策略](/engineering/)，说明共同约定怎样帮助处理冲突、检查结论怎样绑定版本，以及开发成果怎样进入发布快照。

两项工作合并时，需要判断它们能否共同成立。沿用[上一页](./git)的订单例子，先看文本冲突，再看行为冲突，最后确认交付哪个版本。

## 同一处改成两种内容

共同起点的判断只有付款与发货条件：

```js
return isUnpaid(order) && isUnshipped(order);
```

一个任务增加订单归属，另一个任务在同一行增加重复请求检查。Git 无法自动合并这处差异时，会留下冲突，供团队核对。

| 读取的版本 | 改成了什么 | 需要保留的意图 |
| --- | --- | --- |
| 任务 A | 加入 `belongsTo(order, actorId)` | 无权操作应被拒绝 |
| 任务 B | 加入重复取消请求的判断 | 重复请求得到约定的结果 |
| 共同起点 | 只有付款与发货判断 | 原有条件继续成立 |

处理时，先读双方为什么改，再回到共同契约判断最终行为。重复请求可能需要返回已有结果，也可能需要明确拒绝，具体取决于已确认的规则。最终代码应同时满足归属、状态与重复操作约定，再接受相关检查。

可以这样要求团队处理：

> 请说明双方各自实现的要求，给出能同时满足这些要求的合并方案和检查结果。涉及改变取消规则的选择，单独提交决定。

技术组合由 AI 处理；业务承诺发生冲突时，由人裁定并记录相应变更。

## 没有文本冲突，仍要检查共同行为

假设后端在一个文件中将成功响应的字段从 `cancelled` 改成 `status`，前端在另一个文件中继续读取 `cancelled`。Git 可以合并两份文件，页面却可能无法显示正确结果。

此时需要查共同的数据定义与 SYNC 契约：字段应是什么，两端是否实际使用同一来源，再在共同版本走过取消路径。

反馈可以指向具体缺口：

> 合并后的两端读取了不同字段。请对照共享定义修正，并补当前共同版本的取消与反馈证据。

S3 先约定行为和数据，S5 检查计划，S6 集成，S7 检查整体结果，都可以沿这个例子理解。

## 检查结论绑定一个确定对象

“开发分支上的检查通过了”，还缺少检查对象。分支持续接收提交，同一个分支名在不同时间可能指向不同内容。

| 记录 | 应能查到什么 |
| --- | --- |
| 当前承诺 | 哪份 REQ、哪个需求基线 |
| 被测对象 | 哪个共同提交，以及检查所需的配置和环境 |
| 检查结果 | 哪些情形实际执行，结果和证据在哪里 |
| 后续变化 | 检查后又改了什么，哪些结论需要重验 |

例如 M1 的取消检查通过，后来 M2 修改了权限判断。团队需要依据 M2 的影响重新取得相关证据，完整验证按模板规则展开。M1 的报告继续保存其历史含义。

因此，每次报告都要能回答“检查的是哪一份内容”。需求、设计与代码的正式版本也要对得上；本轮事实和授权由运行状态保存，任务工作目录共同使用这一权威入口。

## 开发成果怎样成为发布版本

本模板确定两条用途不同的路线：开发分支接收日常工作，发布上游保留发布快照。名称由项目显式确定。

| 环节 | 本模板怎样处理 | 需要留下什么 |
| --- | --- | --- |
| 任务集成到开发分支 | 保留普通合并提交，联合检查并接收 | 任务来源、共同版本和接收结果 |
| S7～S10 检查交付 | 验证需求与整体风险 | 当前证据、验收、审计和恢复安排 |
| S11 决定发布 | 人明确批准，实际发布由人执行 | 对交付内容、风险和发布时机的决定 |
| 开发成果进入发布上游 | 按规则压缩为发布提交，发布后合回开发分支 | 发布快照与开发历史的来源关系 |

**压缩提交 squash** 把选定的一组开发改动汇成一份发布提交。任务合并保留逐项来源，发布提交描述这次整体交付；交付内容仍需核对检查依据，新增改动重新评估。

项目还可以用 **标签 tag** 为确定提交标注发布名称。推送将 Git 对象和引用传到远程仓库；实际部署则需要项目的发布步骤和环境。报告与发布记录应能说明实际交付了哪份内容。

若上线后需要恢复，还要考虑配置和数据：恢复代码版本不会自动撤回已经发生的数据变化。S10 的迁移与恢复安排因此属于交付依据。

## 用四项事实核对一次交接

```text
起点：从哪个确定的版本开始。
范围：这项工作获准改变什么，依据哪份要求。
交接：成果在哪个提交，是否已合入指定共同版本。
检查：当前结论检查了哪个版本，还缺什么。
```

沿这四项查阅，可以发现输入遗漏、越界改动、尚未集成或证据过期。对应的阶段入口见[机制原理](../mechanism/)，材料位置见[文档地图](../document-map/)。
