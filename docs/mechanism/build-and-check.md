# S6～S7：做出来，再独立验证

这两步回答不同问题：S6 使计划中的工作进入共同版本；S7 检查这个版本是否真的满足承诺。

## S6：构建与接收 {#s6}

- **输入**：S5 锁定的任务批次、完成标准、依赖顺序和授权范围。
- **输出**：每项任务的如实结果、代码与测试、检查记录；成果经合并、联合检查和接收进入 REQ 绑定的开发分支。
- **为什么有这一步**：多名执行者可以在各自的分支和 worktree 工作，但各自报告“完成”之后，项目共同版本仍可能没有这些成果。
- **偏差怎样处理**：实现受阻，在该任务记录阻塞；规格含糊，返回 S5 并追到实际失真的设计或契约；已实现后发现缺陷，交 S8 调查。

任务在个人工作区完成、已经提交、已经合并、已被项目接收，是不同事实。追查“功能明明做了却不在项目里”，应先看 S6 的分支、合并与接收记录。

分支与 worktree 的分工见[版本与工作区](../start/concepts#版本与工作区)。

## S7：进行完整验证 {#s7}

- **输入**：S6 接收的共同版本、REQ 验收标准、设计场景和契约条款；修复后也要从 S9 接收新的版本与重验范围。
- **输出**：本轮验证计划（ReviewPlan）、逐项结果与证据。全部必需维度在同一轮通过或有经独立审查的不适用理由，无未关闭阻断问题、无失效证据时，形成**完整验证通过记录（CleanRound）**。阻断性发现汇成**发现批次（ObservationBatch）**交 S8。正式报告在 `docs/reports/review/`、`docs/reports/qa/`、`docs/reports/e2e/` 查阅。
- **为什么有这一步**：构建者的测试与报告仍是对自己工作的说明。需要独立角色在同一版本、同一轮次检查是否符合约定、工程质量与真实用户行为。
- **偏差怎样处理**：证据遗漏或过期，补齐或重开本轮；发现产品缺陷，进入 S8；发现需求本身需要改动，则暂停并交人裁定。

CleanRound 对应**这一轮、这一版本和声明范围**。S10 随后汇总完整交付，并检查系统风险。

场景检查沿用 S2 的 CASE，并通过 S3 与需求相连。检查者可以补充情形，原有必需项仍要逐项给出结果，或经审查的不适用说明。核对方法见[从承诺查到证据](../document-map/evidence-chain)。
