# S0～S2：从意图到共同设计

这三步形成后续工作的依据：先确定这次要改变什么，再登记本轮授权，最后把需求变成各方可以共同使用的设计。

## S0：确认需求 {#s0}

- **输入**：人的预期效果、项目已有事实；涉及既有模块时，还要参考该模块的当前设计。
- **输出**：经人逐层确认并锁定的 `docs/requirements/REQ-{id}.md`。其中 §A 写目标、背景、成功状态和明确不做；§B 写方向、约束与风险；§C 写具体需求、流程、异常、权限和验收。
- **为什么有这一步**：一句愿望可能同时包含目标、对原因的猜测和对做法的偏好。直接开发，后续工作便可能沿着不同理解前进。
- **偏差怎样处理**：尚未锁定时留在 S0 澄清。已锁定后若发现原承诺有误，进入受控的需求修订；下游依据旧承诺形成的结论需重新评估。

锁定表示**承诺已经确定**，尚不表示后续周期已经获得授权。后者由 S1 记录。

## S1：登记这轮授权 {#s1}

- **输入**：开发分支中一份已提交、已锁定且通过完整性检查的 REQ、人的明确绑定授权，以及确定的开发分支和发布上游。
- **输出**：项目运行状态中的唯一 REQ 绑定、需求指纹和授权记录；运行阶段进入设计。
- **为什么有这一步**：一个工作周期必须知道自己正在兑现哪一份承诺。若需求和版本来源都不确定，设计与证据便无法对到同一基线。
- **偏差怎样处理**：REQ 内容不完整，回 S0；当前周期已有绑定或需改变承诺，走对应的撤销、暂停或需求变更流程。

S1 将授权写入**运行状态**。REQ 上的 `locked` 表示需求已确认；实际开始了没有、走到哪里，要查运行记录。Project Map 可以提供这份记录的摘要。

绑定、暂停、恢复和需求修订的区别，见[跨阶段处理](./lifecycle)。

## S2：建立共同设计 {#s2}

- **输入**：已绑定的 REQ、项目规则、既有架构；涉及模块行为时，还需读取该模块原有的场景与故事。
- **输出**：锁定的 `docs/architecture/ARCHITECTURE-*.md` 和必要的设计决策记录。界面或行为受影响时，还要在 `docs/design/prototypes/<module>/` 维护模块**完整的当前场景、故事、路径与原型**。正式用户故事在此依据 REQ 的意图展开。
- **为什么有这一步**：需求说明要达到什么，却尚未说明模块职责、状态变化和用户路径。各执行者若自行补全这些内容，可能得到彼此冲突的实现。
- **偏差怎样处理**：设计细节缺漏，在 S2 补齐；设计发现原本业务承诺无法成立，交回人处理需求变更。

模块包保留该模块的完整当前设计，REQ 作为变化来源被引用。它说明行为**应如何运作**；功能是否已经实现，要看后续的构建和验证。

场景包中的检查情形 `CASE` 对应需求验收标准，后续契约、任务和验证沿用这些关系。AI 架构与设计角色完成设计定稿；改变业务承诺时，由人确认变更。
