# S8～S9：查明原因，修复后重新证明

发现问题后，先确定原因和影响范围，再在明确边界内修改。局部修复通过以后，还要回到完整验证轮。

## S8：调查发现 {#s8}

- **输入**：S7 的 ObservationBatch 与原始证据，或其他受控来源的阻断发现；同时读取当前 REQ、设计、契约、任务和已实现版本。
- **输出**：调查案例 **InvestigationCase**、可检验的根因解释与影响范围；确属实现缺陷时形成经批准的 **RepairContract**，写明修复目标、允许范围和完成判据。这些结构化对象从运行状态中的证据引用进入。`docs/reports/bugs/` 的 BUG 文档可能提供可读报告，但不代替上述调查与修复依据。
- **为什么有这一步**：一个可见症状可能来自实现、规格或需求本身。看到“取消按钮无响应”便直接修改代码，可能只消除表象。
- **偏差怎样处理**：根因仍不清楚，继续调查；规格错误，回产生错误的设计或契约阶段；人的业务承诺需要变化，暂停并交人处理。

要判断从哪里打回，S8 是主要的**归因位置**：它把“哪里表现异常”推进到“哪一层先出了错”。

## S9：执行有边界的修复 {#s9}

- **输入**：S8 已批准、绑定当前版本的 RepairContract，以及它引用的发现、根因与修复边界。
- **输出**：修复计划与结果、真实改动范围 **ChangeImpact**、独立的定向复验 **TargetedReverification**，以及返回完整验证的 **RepairHandoff**；从运行状态中的修复证据引用进入。受影响的旧证据被标记失效。
- **为什么有这一步**：修复会改变被测对象。旧版本曾经通过的检查，不能继续为已修改的版本作证；只验原来的故障，也不足以证明整体仍然可靠。
- **偏差怎样处理**：定向复验仍失败，回 S8 重查原因；修复揭示规格错误，回 S2 等相应上游；定向复验通过，则回 **S7 开启新一轮完整验证**，不能直接进入验收。
