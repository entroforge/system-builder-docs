# S8～S9：查明原因，修复后重新证明

发现问题后，先确定原因和影响范围，再在明确边界内修改。局部修复通过以后，还要回到完整验证轮。

## S8：调查发现 {#s8}

- **输入**：S7 的发现批次（ObservationBatch）与原始证据，或其他受控来源的阻断发现；以及当前 REQ、设计、契约、任务和已实现版本。
- **输出**：调查记录（InvestigationCase）、根因解释与影响范围；确属实现缺陷时，形成经批准的修复约定（RepairContract），写清目标、允许范围和完成标准。当前记录由运行状态中的证据引用指向，`docs/reports/bugs/` 可提供便于阅读的 BUG 报告。
- **为什么有这一步**：一个可见症状可能来自实现、规格或需求本身。看到“取消按钮无响应”便直接修改代码，可能只消除表象。
- **偏差怎样处理**：根因仍不清楚，继续调查；规格错误，回产生错误的设计或契约阶段；人的业务承诺需要变化，暂停并交人处理。

S8 要解释的是：**问题为什么出现，哪一层先出错，其他地方是否有同类问题。** 根据这个结果，才能决定重做哪里。

范围内的修复约定由主协调者或架构角色批准。调查若提出改变需求、预算或其他人的授权边界，应提交具体选项和影响，由人决定。

## S9：执行有边界的修复 {#s9}

- **输入**：S8 已批准、绑定当前版本的修复约定（RepairContract），以及相关发现、根因与修复边界。
- **输出**：修复计划与结果、实际改动影响清单（ChangeImpact）、针对原问题的独立复验（TargetedReverification）、返回完整验证的交接记录（RepairHandoff）。运行状态保存这些证据引用，受影响的旧证据被标记失效。
- **为什么有这一步**：修复会改变被测对象。旧版本曾经通过的检查，不能继续为已修改的版本作证；只验原来的故障，也不足以证明整体仍然可靠。
- **偏差怎样处理**：定向复验仍失败，回 S8 重查原因；修复揭示规格错误，回 S2 等相应上游；定向复验通过，则回 **S7 开启新一轮完整验证**，不能直接进入验收。
