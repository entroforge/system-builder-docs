# S3～S5：把设计变成可交接的工作

设计要先变成各部分一致的约定，再拆成能执行的任务，最后让独立审查者检查整条链。

## S3：形成契约 {#s3}

- **输入**：已锁定的 REQ、S2 架构，以及适用的模块场景与故事。
- **输出**：`docs/dev/contracts/CONTRACTS-{id}.md` 汇总本次条款；适用时生成 FE、BE、SYNC 契约，写清输入输出、状态、拒绝、权限与副作用。需求验收标准应能找到对应条款。
- **为什么有这一步**：前端、后端和联调工作都依赖同一行为。若各自从设计推测接口与错误处理，单独完成也可能无法一起工作。
- **偏差怎样处理**：条款遗漏或两端矛盾，在 S3 修订；共同设计不足，回 S2；发现原需求本身失真，进入人的需求变更。

想知道“取消订单成功后页面与服务端是否说的是同一种成功”，先查 S3 的共同契约。

先确定共享数据定义与 SYNC 的共同行为，再展开 FE、BE 合同。两端通过代码生成或数据校验实际采用共同定义，独立检查核对集成后的结果。AI 规划角色完成契约定稿；改变需求或既有兼容承诺时，按变更规则裁定。

## S4：拆分任务与依赖 {#s4}

- **输入**：S3 已锁定的契约及其条款集合。
- **输出**：`docs/dev/tasks/TASK-*.md` 写每项任务的职责、可读输入、工作范围、依赖和完成标准；`docs/dev/tasks/index-REQ-{id}.md` 汇总任务及派发计划。依赖关系组成无环图，以便识别真正可并行的工作。
- **为什么有这一步**：契约说明系统必须满足什么，还没有明确每项工作由谁完成、先后如何安排、什么证据算交付。
- **偏差怎样处理**：任务遗漏、职责混杂或依赖有误，留在 S4 重排；契约自身缺少条款，则回 S3。

任务文档写成 `complete` 表示**计划可以交审**，不表示代码已完成。

例如，共同定义先完成，页面与后端再按依赖展开；互不依赖且没有资源冲突的任务可以并行。“无环图”的含义见[依赖与并行](../start/concepts#依赖与并行)。

## S5：动工前独立检查 {#s5}

- **输入**：S3 的契约、S4 的任务与整体派发计划，以及它们依据的需求和设计；这些材料均指向确定的版本。
- **输出**：两路审查结论、必要的 `docs/reports/review/REV-*.md` 发现记录；通过后，运行状态中形成锁定的执行批次。
- **为什么有这一步**：规划者可能以为某个条件已经写清，执行者却找不到依据。独立审查分别检查规格是否一致、任务能否执行。
- **偏差怎样处理**：发现落在哪份上游产物，就修对应的 S2、S3 或 S4 内容，再审受影响部分；若必须改动已锁定的业务承诺，交回人裁定。

S5 的通过说明**计划可以交给构建者**，尚不证明软件已经符合需求。
