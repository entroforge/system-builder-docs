# 暂停、修订与下一项需求

S0～S11 描述一项需求的工作过程。暂停、改变承诺、撤回授权和结束周期，会影响整个过程，因此另有跨阶段的处理方式。

## 每种动作接收什么，改变什么

| 动作 | 输入与决定主体 | 输出与去向 |
| --- | --- | --- |
| **绑定 bind** | 人确认本轮处理哪份已锁定 REQ，以及开发分支与发布上游 | 形成唯一绑定，按 S1 进入设计 |
| **暂停 pause** | 人要求暂停，或机制发现需要停止推进的问题 | 保存当前位置、输入版本和暂停原因，等待处理 |
| **恢复 resume** | 人批准继续；机制核对暂停时的输入未变 | 回到保存的位置，接着处理原工作 |
| **修订 amend** | 先暂停；人确认同一 REQ 的更高版本，形成新锁定基线 | 同一周期换用新基线，下游旧证据失效，回 S2 重建依据 |
| **撤回 unbind** | 本轮尚未进入终态；人撤销授权，并说明理由 | 归档本轮记录，清空活跃绑定；该 REQ 可按条件再次绑定 |
| **中止 abort** | 人决定结束本轮；从暂停处或 S11 作出 | 进入中止终态，随后按人的授权归档 |
| **批准 approve** | 人在 S11 接受交付与剩余风险 | 形成发布授权，进入授权终态；实际发布由人执行 |
| **归档 rollover** | 已批准或已中止的终态周期，以及人的归档授权 | 保存周期历史，REQ 留下归档标记，建立空闲的新周期 |

**暂停留下继续工作的入口；中止结束本轮；撤回取消当前绑定。** 三者都应留下发生原因和已有工作的记录。

## 暂停后，先核对有没有变化

例如验证途中临时停下。恢复时，程序会核对暂停时保存的输入版本：原需求与已登记材料仍一致，才可接着原位置工作。

暂停期间若直接改了锁定需求，恢复检查会发现不一致。这时需要处理变更，重新判断旧成果还能证明什么。**基线**就是本轮共同依据的确定版本；**指纹**是程序识别文件内容是否改变的摘要。

S11 的“搁置”则表示暂未作发布决定，继续等待人再议。它发生在交付出口，与工作途中保存检查点的暂停有不同位置。

## 承诺改变，旧结论重新评估

原承诺是“未付款、未发货的本人订单可以取消”，后来希望纳入已付款订单。这改变了需要实现和检查的行为。原来通过的报告仍可供查阅，但不能直接为新承诺作证。

修订从暂停状态开始，使用同一 REQ 编号的更高版本，保留同一运行周期的历史，使下游旧证据失效。团队回 S2，依据新基线重新组织设计、契约、任务和验证。已有代码可能可以复用，是否适合新承诺仍需检查。

修复实现缺陷则沿 S8～S9 处理，依据改动影响重新取证。**需求修订影响承诺依据，缺陷修复影响实现依据**；两者决定了不同的重做范围。

## 反复修不好时，回到人的判断

模板支持为修复次数、同一判据反复失败和完整验证轮数设置上限。达到项目已启用的相应限制后，按规则暂停或拒绝继续，并交人处理。限制是否启用及具体额度由项目配置决定。

此时应说明重复的问题、已经尝试的办法、剩余缺口与继续投入的建议。人可以判断是否增加投入、回到设计治理、修订范围或中止。取消原来的检查要求，涉及承诺变化，需要明确处理。

## 一项结束，项目继续

批准或中止后，按授权归档本轮运行记录，再建立新的空闲周期。下一项需求经过确认、锁定和绑定，开启自己的工作过程。

项目的代码、架构、模块设计和稳定规则继续存在。下一份 REQ 描述对它们的新变化；上一轮的任务与报告保留为历史。新周期需要取得适用于自己的证据。

查这些资产的不同存续范围，可回到[文档地图](../document-map/#材料会保留多久)；人的日常管理见[把握进度与干预](../engineering/management)。
