# S10～S11：交付材料与人的决定

完整验证通过以后，仍需确认整项承诺已经兑现、系统能够承受这次变更，以及剩余风险由谁承担。

## S10：验收与发布审计 {#s10}

- **输入**：S7 当前有效的 CleanRound；锁定的 REQ、契约与任务判据；构建和修复证据；部署、迁移、回滚等交付资料。
- **输出**：`docs/reports/acceptance/ACC-*.md` 及其证据清单；`docs/reports/release-audits/` 中的发布审计材料；风险与技术债记录；交给 S11 的发布就绪包。
- **为什么有这一步**：验证轮检查了声明范围内的结果，尚未汇总每项承诺与证据的对应关系，也未完整判断迁移、事务、并发、恢复等系统级风险。
- **偏差怎样处理**：证据不完整，回相应验证环节；审计发现产品缺陷，进入 S8；发现需求缺口，暂停并交人裁定。只有当前 CleanRound 仍有效，交接包才成立。

验收对照用户与需求承诺，审计对照系统整体性质。查“整项 REQ 是否兑现”，先看验收材料；查“本次发布会不会破坏系统”，再看发布审计。

## S11：人作发布决定 {#s11}

- **输入**：S10 的发布就绪包、当前有效的验证与审计证据、剩余风险、影响和恢复点。
- **输出**：明确的人类决定及运行记录。批准形成发布授权；搁置进入等待；驳回缺陷进入 S8；驳回验收或发布审计返回 S10 对应环节；中止关闭本轮周期。
- **为什么有这一步**：工程检查可以提供事实，发布时机、业务代价和风险承担仍需由人决定。通过检查不会自动成为发布批准。
- **偏差怎样处理**：按决定的类型进入固定返回路径。批准只代表这轮生命周期获得发布授权，实际发布动作仍由人执行。

S11 是判断结果的出口。若这里发现“做出来的不是原来想要的”，应沿 S10 的验收证据回查到最早失真的 REQ、设计或实现，再走相应的调查或需求变更流程。
